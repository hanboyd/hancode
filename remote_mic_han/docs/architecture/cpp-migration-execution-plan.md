# RemoteMic Windows C++ 渐进式重构执行路线

- 文档状态：Draft
- 编写日期：2026-08-29
- 适用产品：Windows RC003 独立版本
- 当前基线：Python 3.11 + PySide6 产品实现；C++20/CMake 仅包含基础框架、诊断 CLI、运行目录、日志及 `IBleTransport` / `IAudioRoute` 初始接口

## 1. 目标

在不丢失当前已验证产品行为的前提下，将适合原生实现的模块逐步迁移到 C++20，最终让 C++ 核心负责协议、会话、音频、Windows 输入和 BLE 等关键能力。

迁移期间必须始终保留一个可运行、可安装、可回退的 Windows 版本。每次只替换一个边界，旧实现至少保留到新实现通过离线回归、Windows 集成验证和相应真实设备验收之后。

## 2. 不在本路线中直接完成的事项

- 不进行一次性全量重写。
- 不在核心迁移完成前重写 PySide6/QML 设置界面。
- 不开发自定义虚拟麦克风驱动或 HID 驱动。
- 不把 VB-CABLE 替换工作与 C++ 核心迁移绑定在同一个阶段。
- 不修改第三方输入工具，不补丁其已签名可执行文件，也不降低 Windows 安全边界。
- 不把编译成功、单元测试或日志正常等同于 RC003、音频端点或目标输入工具的真实验收。

## 3. 全程必须遵守的迁移规则

1. **行为先固定，代码后迁移。** 每个模块迁移前，先把 Python 现有行为写成测试向量、状态转换表或回放数据。
2. **核心与平台分层。** 纯协议和会话逻辑不得依赖 WinRT、Qt、PortAudio、Python 对象或 Windows 句柄；平台类型只能出现在基础设施适配器中。
3. **单模块替换。** 每个阶段只允许一个新的主变量，禁止同时替换协议、音频、BLE 和 UI。
4. **双实现可切换。** 迁移期每个边界至少支持 `python` 和 `native` 两种实现；纯函数模块可增加 `shadow` 模式进行同输入比对。
5. **影子模式不得产生双重副作用。** 协议解码可以同时运行并比对；音频写入、按键注入和 BLE 写操作只能由一个实现拥有。
6. **队列必须有界。** BLE 回调、低级键盘钩子和音频回调中不得执行阻塞文件、进程、设备打开或日志刷新操作。
7. **保持用户数据兼容。** `config.json`、`key_bindings.json`、使用统计和日志位置在迁移期间保持向后兼容。
8. **保持安装升级合同。** 继续使用稳定 AppId 和安装位置，升级时保留用户数据并只留下一个已安装应用条目。
9. **真实验收单独记账。** 使用 `passed`、`failed`、`deferred`、`not_applicable`；没有物理 RC003 或目标应用观察时必须标记 `deferred`。
10. **每个架构变化先写 ADR。** 尤其是 Python/C++ 绑定方式、线程所有权、音频后端、BLE 生命周期和 UI 去留。

## 4. 目标架构

```text
PySide6/QML 设置界面（迁移期保留）
              │
       Python 应用协调层
              │
       薄绑定层 remotemic_native
              │
┌──────────── C++20 核心 ────────────┐
│ ATVV 协议 / ADPCM / 会话状态机      │
│ 有界队列 / 诊断事件 / 配置值对象    │
└──────────────┬──────────────────────┘
               │ 纯虚接口
┌──────────── Windows 基础设施 ───────┐
│ WASAPI │ WinRT BLE │ Raw Input      │
│ LL Hook│ SendInput │ 运行目录/日志  │
└─────────────────────────────────────┘
```

推荐先用一个很薄的 `pybind11` 扩展承接 Python/C++ 过渡。绑定层只负责类型转换、异常翻译和生命周期桥接，业务规则必须留在可被纯 C++ 测试直接调用的 `remotemic_core` 中。是否采用 `pybind11` 应先通过新的 ADR 正式确认；如果改用稳定 C ABI，下面的阶段顺序不变。

## 5. 执行步骤

### 阶段 0：冻结可迁移的产品基线

**要做的事**

- 审查当前工作树，把已经由用户在 RC003、Typeless、Qianwen 和安装升级上接受的行为整理成一个明确的基线提交或标签；不得混入无关改动。
- 记录当前支持的设备、音频格式、按键语义、配置默认值、日志位置、安装位置和用户数据兼容要求。
- 将 ADR-0003、ADR-0006、ADR-0007、ADR-0008、ADR-0009、ADR-0010 中的约束转成迁移检查表。
- 保存无隐私的合成 ATVV 数据、状态转换样例、音频输入样例和配置样例；禁止保存真实语音、蓝牙地址、设备路径和第三方账号信息。
- 运行当前 Python 全量回归、C++ 构建/CTest、冻结程序 `--dry-run`、公开边界扫描，并记录命令和结果，不把会漂移的测试数量写成永久门槛。

**阶段产物**

- 一个可复现的基线提交或标签。
- 一份“行为合同清单”，列明所有后续实现必须保持的输入、输出、时序、错误和清理行为。
- 一组不含真实设备或个人数据的回放夹具。

**退出门禁**

- 当前产品回归为 `passed`。
- 当前 C++ 框架构建和 CTest 为 `passed`。
- 需要真实硬件或第三方应用的项目有最新验收记录，否则明确为 `deferred`。
- 基线不满足时停止迁移，先恢复产品基线。

### 阶段 1：建立 Python/C++ 共存和回退框架

**要做的事**

- 新建 ADR，确定绑定技术、异常边界、线程/对象所有权、二进制兼容策略和打包方式。
- 将 CMake 目标拆成：纯核心库、Windows 基础设施库、Python 扩展、C++ 单元测试；禁止 Qt、WinRT 和音频后端泄漏到纯核心库。
- 在 Python 配置或开发开关中加入模块级实现选择：`python`、`native`；只对无副作用模块开放 `shadow`。
- 定义统一错误模型和诊断事件，日志中只记录模块、状态、错误类别和耗时，不记录蓝牙标识或语音内容。
- 让 PyInstaller/安装包能够携带并加载原生扩展；加载失败时回到 Python 实现并留下明确诊断，而不是让应用无法启动。
- 在 CI 中增加 MSVC Debug/Release 构建、C++ 单元测试、Python 绑定导入测试和冻结包加载测试。

**阶段产物**

- 可由 Python 成功导入的最小 `remotemic_native`。
- 一个无业务逻辑的原生探针函数和完整打包验证。
- 模块级开关及可验证的回退路径。

**退出门禁**

- Python-only 路径行为不变。
- 原生扩展在源码运行、冻结目录和安装目录中都能加载。
- 删除或损坏原生扩展时，应用能安全回退且不损坏配置。

### 阶段 2：迁移 ATVV 协议与 ADPCM 解码

这是第一项生产功能迁移，因为该模块接近纯计算、已有合成夹具和明确测试面，且不会直接控制系统设备。

**要做的事**

- 将 ATVV 能力解析、控制消息编码、IMA/DVI ADPCM 解码和 PCM 格式约束移入纯 C++ 核心。
- 明确定义字节序、位宽、溢出/饱和、畸形包、空包、分包和不支持能力的处理方式。
- 把 Python 现有测试向量逐项移植为 C++ 参数化测试；同一夹具同时喂给 Python 和 C++。
- 在 `shadow` 模式逐样本比较控制结果和 PCM 输出；任何差异都必须先解释并补测试，不能靠容差掩盖整数算法差异。
- Python 继续拥有 BLE、音频和会话协调，只把字节输入交给 C++ 并接收结构化结果。

**阶段产物**

- C++ ATVV/ADPCM 模块及纯 C++ 测试。
- Python 薄适配器。
- Python/C++ 黄金样例一致性报告。

**退出门禁**

- 所有合成样例实现逐字节或逐样本一致。
- 畸形输入不会越界、崩溃或产生无限分配。
- Python 全量回归保持 `passed`。
- 该阶段不需要真实硬件，硬件项记为 `not_applicable`；进入下一阶段前可用真实 RC003 做一次只读回归确认。

### 阶段 3：迁移会话状态机和时序规则

**要做的事**

- 将 `VoiceController`、ATVV 会话边界、200 ms 释放消抖、2.5 秒稳定停止回退及关闭动作重试所有权抽成纯 C++ 状态机。
- 把时间作为可注入时钟或显式事件时间传入，测试不得依赖真实睡眠。
- 将 TOGGLE 的“开 TAP—持续音频—排空—关 TAP”和 HOLD 的 `KEY_DOWN/KEY_UP` 写成状态转换表。
- 覆盖重复按下、固件抖动、中途 AUDIO_STOP、AUDIO_START 恢复、断连、关闭 TAP 失败、重连、应用退出等路径。
- Python 只负责执行 C++ 返回的命令，不得在两个语言层各保存一份会话真相。

**阶段产物**

- 确定性 C++ 会话状态机。
- 从现有 Python 行为生成的事件回放集。
- 单一 owner 和失败清理说明。

**退出门禁**

- 每个物理会话至多产生一个主机会话。
- TOGGLE 至多一个开启 TAP 和一个关闭 TAP；HOLD 的 down/up 必须配对。
- 200 ms 默认值及 `[0.050, 0.500]` 限制不变，除非另立 ADR。
- 离线回放一致后，用真实 RC003 对 Typeless 与 Qianwen 分别验收；目标窗口、音频、释放和转写需由用户实际观察。

### 阶段 4：迁移音频队列与 WASAPI 输出

**要做的事**

- 先把有界 PCM 队列、20 ms 分块、静音补帧、丢弃最旧数据、排空和关闭策略移入 C++，再实现 `IAudioRoute` 的 WASAPI 后端。
- 使用独立写线程；BLE/协议回调只进行有界入队，不打开设备、不写文件、不等待音频端点。
- 保持 16 kHz、单声道、16-bit PCM 合同，并显式处理 Windows 端点格式协商和重采样责任。
- 保持两秒队列上限和有界排空；变更这些产品时序前必须立 ADR。
- 增加假的音频端点，测试启动、连续静音、音频突发、溢出、设备消失、默认设备切换、排空超时和关闭幂等。
- 先在回放模式比较样本计数、峰值、RMS、丢帧计数和排空顺序，再切换真实 WASAPI 输出。

**阶段产物**

- C++ 有界音频管线和 `WASAPIAudioRoute`。
- 无声的合成环回测试与诊断计数器。
- Python 音频实现的可切换回退路径。

**退出门禁**

- 音频队列内存上界可证明，停机可在规定时间内完成。
- 合成 PCM 到目标虚拟端点的格式、幅度和连续性验证为 `passed`。
- 使用真实 RC003 和目标输入工具完成一次音频/转写验收；自动化只能证明程序侧输出，不能代替该门禁。

### 阶段 5：迁移 Windows 输入采集与动作发送

**要做的事**

- 分三个独立提交迁移：Raw Input 解析、低级键盘钩子/抑制、`SendInput` 动作发送；不得合并为一次大替换。
- 定义 `IInputSource`、`IHostActionSink` 等新接口，并用 ADR 记录线程与回调时限。
- 低级钩子只更新原子状态和无阻塞入队，绝不等待锁、音频、进程、文件或 Python GIL。
- 保持 direct HID、被吞掉的 F5、Raw Input 三条来源的单一 owner 规则和现有诊断含义。
- 保持用户的 `key_bindings.json`；不得把 back、volume_up、volume_down 硬编码为固定动作。
- Qianwen 特定物理化逻辑留在隔离适配器中，继续按已验证版本 fail closed；核心状态机不得依赖进程名或窗口标题。

**阶段产物**

- C++ Windows 输入源与动作接收器。
- 可回放的 HID/键盘事件测试。
- 钩子耗时、丢弃计数、队列深度和动作结果诊断。

**退出门禁**

- 钩子回调满足非阻塞要求，压力测试下不泄漏 F5、不产生重复会话。
- 常规按键、语音键、back 和音量键的现有映射行为保持一致。
- Notepad、Typeless、Qianwen 与真实 RC003 的观察结果分别记录；任何未实际观察的应用边界标记 `deferred`。

### 阶段 6：迁移 BLE/WinRT 传输

BLE 放在协议、会话和音频之后，以便把硬件问题限制在传输层，并使用已验证的上层核心处理回放数据。

**要做的事**

- 用 C++/WinRT 实现 `IBleTransport`，把设备发现、连接、服务/特征选择、通知订阅、写入和断连清理封装在基础设施层。
- 明确 apartment、线程、取消、超时和回调对象的生命周期；回调不得持有悬空 `span` 或跨线程裸指针。
- 为发现为空、权限拒绝、特征缺失、连接中断、重复通知、写失败和应用退出建立假 WinRT 测试。
- Python 与 C++ BLE 后端不能同时连接同一 RC003；对硬件只允许单 owner。
- 日志只记录匿名状态和错误类别，不记录 MAC、设备实例路径、服务 UUID 或其他可识别信息。

**阶段产物**

- `WinRTBleTransport` 和可注入的假传输。
- 连接/重连状态机测试与资源清理测试。
- Python BLE 后端回退开关。

**退出门禁**

- 无硬件测试、断连/重连测试和关闭清理均为 `passed`。
- 真实 RC003 的发现、连接、音频通知、控制写入、断连和再次连接由实际运行确认。
- 如果硬件不可用，本阶段保持 `deferred`，不得进入删除 Python BLE 实现的步骤。

### 阶段 7：把应用协调层移入 C++

**要做的事**

- 在协议、会话、音频、输入和 BLE 都独立通过门禁后，将 `app.py` 中的生命周期协调逐段移入 C++ `Application`。
- C++ 成为设备连接、会话状态、音频路由、输入 owner、重连和关闭清理的唯一真相源。
- Python 仅保留设置 UI、配置展示、统计展示和少量第三方适配器；通过命令/事件 API 与 C++ 通信。
- 为每个跨语言命令定义序号、完成/失败结果和幂等要求，防止 UI 重复点击造成双启动或双关闭。
- 保持应用内桥接重启、单实例、日志、统计和安装升级行为。

**阶段产物**

- 可由现有 PySide6 UI 驱动的 C++ 应用服务。
- 统一的命令/事件接口。
- Python 协调代码删除清单，但此阶段暂不删除仍用于回退的实现。

**退出门禁**

- 源码运行、冻结程序、安装升级、桥接重启、休眠/唤醒后的关键行为均完成验证。
- 配置、键位、统计和日志在原位升级后保持。
- 真实 RC003 + 两个目标输入工具的完整路径通过用户验收。

### 阶段 8：打包切换并淘汰旧 Python 核心

**要做的事**

- 先让发布候选默认使用 `native`，继续保留一个版本周期的 Python 回退开关。
- 对 Release 二进制执行依赖、签名状态、公开边界、崩溃转储隐私和安装覆盖检查。
- 用旧安装版直接升级到新候选，确认进程被正确停止、程序载荷被替换、用户数据保留且只出现一个已安装条目。
- 观察一个完整稳定周期后，按模块删除 Python 旧实现；每次删除都运行全量回归和打包验收。
- 删除回退实现前归档其行为夹具和 ADR，不删除可用于回归的黄金样例。

**阶段产物**

- 默认使用 C++ 核心的 Windows 安装包和便携包。
- 旧 Python 核心的分模块删除记录。
- 发布验证报告和仍未完成的外部验收清单。

**退出门禁**

- 原位升级合同、隐私扫描、冻结程序启动和完整产品回归全部 `passed`。
- 真实设备和目标应用验收全部有明确状态。
- 出现影响使用的回归时，发布回退到上一安装候选，而不是在现场继续扩大重构范围。

### 阶段 9：单独决定 UI 是否迁移

此阶段不是 C++ 核心迁移的必然组成部分。只有在 C++ 协调层稳定、PySide6 成为明确维护或发布负担时，才评估 Qt 6 C++、WinUI 3 或继续保留 PySide6。

**要做的事**

- 新建 ADR，对安装体积、无障碍、视觉一致性、开发成本、自动化测试和 Windows 版本支持进行比较。
- 如果保留 PySide6，删除已无用的业务代码，只保留 UI 客户端。
- 如果迁移 UI，按页面逐个替换，并以当前截图、键盘导航和设置读写测试作为合同；不得与驱动或 BLE 改造同时进行。

**退出门禁**

- UI 选择有独立证据和 ADR。
- 所有设置、诊断、统计、权限提示、单实例和桥接控制行为保持一致。

## 6. 每个迁移阶段的标准工作单

每个模块都按下面的固定顺序执行：

1. 写清模块边界、owner、线程、输入输出、错误和清理合同。
2. 从 Python 实现提取无隐私夹具和边界测试。
3. 新增或更新 ADR。
4. 写纯 C++ 单元测试，再实现 C++ 模块。
5. 接入薄绑定层，默认仍使用 Python。
6. 用 `shadow` 或离线回放比较；副作用模块只使用假后端比较。
7. 切换开发环境到 `native`，运行聚焦回归。
8. 运行 Python 全量回归、C++ CTest、冻结程序和公开边界扫描。
9. 对实际受影响的设备/端点/目标应用做真实验收。
10. 生成安装候选并验证原位升级。
11. 保留回退开关，观察稳定后再删除旧实现。
12. 更新 `CURRENT_STATUS.md`、`AI_HANDOVER.md`、测试证据和剩余风险。

## 7. 统一验收表

| 验收面 | 自动化可证明 | 必须额外实际观察 |
|---|---|---|
| 协议/ADPCM | 字节、样本、错误处理完全一致 | 通常不需要 |
| 会话状态机 | 动作顺序、次数、超时、清理 | 目标窗口是否只开关一次 |
| 音频管线 | 格式、边界、峰值、RMS、排空、内存上限 | 虚拟麦克风及目标工具是否真正收到并转写 |
| 输入 | 回放解析、钩子时限、动作调用结果 | 真实 RC003 是否泄漏或重复按键 |
| BLE | 假传输、状态机、资源清理 | 真实设备发现、通知、写入和重连 |
| UI/配置 | 读写、迁移、截图、单实例 | 可用性和实际交互 |
| 安装 | 文件、哈希、进程停止、数据保留逻辑 | 真实旧版覆盖升级和 Windows 应用条目 |

## 8. 暂停或回退条件

出现以下任一情况，立即停止下一阶段并恢复上一稳定实现：

- Python 与 C++ 对同一夹具产生无法解释的差异。
- 新实现改变已接受的语音键、音频排空、Qianwen/Typeless 预设或配置兼容行为。
- 回调中出现阻塞 I/O、无界队列、未受控线程或关闭时悬挂。
- 原生扩展导致冻结程序、安装升级或回退路径失效。
- 日志、夹具、崩溃转储或发布包包含隐私数据。
- 仅有自动化证据，却准备把真实硬件或第三方应用状态写成 `passed`。

## 9. 推荐提交粒度

每个阶段至少拆成以下提交，不使用“整个模块一次完成”的大提交：

1. 合同、夹具和测试。
2. 不接入生产路径的 C++ 实现。
3. 绑定/适配与默认关闭的开关。
4. 影子比对或假后端验证。
5. 原生路径切换与回退验证。
6. 文档、打包和验收证据。

这样任何一步都可以独立审查、回退和定位回归，也能在模型或开发者切换时形成可执行交接点。
